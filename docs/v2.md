# V2 — reliable text retrieval and automatic updates

V2 makes the searchable library stay useful as files change. The first build already contained most planned retrieval/indexing components; this milestone completes their automatic-update workflow and its acceptance checks.

| Planned capability | Status and evidence |
| --- | --- |
| Code indexing | Java/Python function parsing, symbol/line provenance; other supported languages use line/token fallback |
| Hybrid retrieval | Literal FTS5 BM25 + text cosine + RRF, optional local cross-encoder; keyword/no-match regression tests |
| Metadata filters | Root, modality, extension, relative path, modified dates applied before candidate limits |
| Incremental indexing | Size/mtime fast path, SHA-256 verification, text embedding reuse, atomic revisions, rename/delete reconciliation |
| Background jobs | Persisted queue, counters, cancellation, per-file errors, interrupted-job recovery |
| Automatic updates | Saved Watch folders control, one-second event debounce, full verification every 15 minutes, visible fallback status |
| Duplicate detection | Exact SHA-256 duplicates grouped with eligible aliases; original files preserved |
| Evaluation | Independent fixture judgments, ranking/no-match/evidence metrics, timings and model/profile identities; measured limitations documented |

## Try the automatic-update workflow

1. Restart Fileora after updating the code and refresh the browser. Setup and model downloads are unnecessary for this milestone.
2. Open **My library** and enable **Watch folders**. The preference is saved per catalog. Selected folders receive an initial verification when enabled.
3. Create a text note containing a distinctive term. After the background scan completes, search for it.
4. Edit the term, rename the file, then delete it. The next searches should reflect the content/path changes and removal without pressing Rescan.
5. Restart normally: the switch should retain its value. Turning it off stops automatic scans; queued/running scans finish. Manual Rescan and Verify all files remain available.

Watching works while Fileora is running. It is off by default for a new catalog. A missing folder is preserved as unavailable, and no deletion is inferred from an incomplete scan. If a native watcher fails, the Library shows the affected path and periodic full scans continue. Restored roots are reattached during that reconciliation. Native events are not a guarantee of immediate updates; debounce, extraction, and queued work add delay.

The CLI `serve --watch` and `serve --no-watch` override the saved choice for that run. The Windows start script's `-Watch` is an explicit override; omit it to follow the saved Library preference.

## Acceptance checks

- Real Watchdog events create, rename, edit, and delete indexed files without manual job submission. A same-size edit with restored mtime still updates the index.
- Turning watching off clears pending hints and prevents newly created files from triggering automatic jobs.
- The preference survives service reconstruction; an explicit startup override takes precedence without changing the saved value.
- Hidden/dependency/excluded paths and unsupported-file events do not dirty the library. Relevant moves retain both source and destination hints.
- Directory events force hashes of descendants, and periodic scans recover a temporarily unavailable root.
- Schedule/start failures and dead emitter threads are visible; the worker remains available for full reconciliation.
- Watch updates require the local session token. Repeating the same setting is idempotent.
- Library controls survive page reload and fit the existing desktop/mobile workspace.

Run `scripts/check.ps1` for the full suite. Focused backend checks are `pytest backend/tests/test_watching.py -q`; browser checks are `npm run test:e2e -- --grep "automatic updates"` from `frontend`, against a running authored-demo server. Existing retrieval results remain in [evaluation.md](evaluation.md); this milestone makes no new relevance or throughput claims.

## Concepts to understand personally

**Watcher hints versus filesystem truth:** operating systems can coalesce/drop notifications. Reconciliation discovers the actual state; forced hashing catches edits that metadata alone misses.

**Atomic publication:** extraction and embedding finish before one SQLite transaction publishes the new revision. The previous content is hidden while changing, and uncommitted failed/cancelled work cannot masquerade as a current result.

**Cache identity:** content hashes and immutable model profiles determine safe text-vector reuse. A filename or timestamp alone is not a content identity.

**Ranking versus answerability:** RRF combines ranks rather than model-space scores. Strong semantic neighbors can still be wrong; conservative match policies reduce misleading results at some cost to recall.

**Lifecycle and recovery:** observer changes are serialized, pending events are debounced, one worker publishes revisions, and shutdown retains catalog ownership until processing stops. These are useful interview topics because each addresses a concrete failure mode.
